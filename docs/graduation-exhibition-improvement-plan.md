## 1. 개발 목표와 우선순위

1학기에 구현하고 발표한 졸업 프로젝트를 제한된 기간 안에서 안정적으로 개선한다. 새로운 서비스를 만들거나 기존 구조를 전면 교체하는 것이 목표가 아니다.

개발 순서는 다음과 같이 유지한다.

1. **기존 코드의 실제 결함 수정**: 보안, 동시성, 데이터 보존·정합성, Calendar 연동, 예외 처리, 잘못된 상태 표시 등.
2. **기존 추천 알고리즘의 정확성과 추천 품질 개선**: 기존 규칙과 점수제를 유지하면서 요청 조건 반영, 대안 탐색, 후보 다양성, 설명을 개선한다.
3. **위 작업 완료 후 Open Design을 활용한 UI 개선**: 안정화된 기능과 정책을 바탕으로 화면을 다듬는다.

오류 복구 버튼이나 사실에 맞는 상태·추천 문구처럼 기능을 정상적으로 사용하기 위한 최소 UI 수정은 1~2단계에 포함될 수 있다. 이를 3단계의 Open Design 기반 시각 개선과 구분한다.

### 유지할 원칙

- Java 규칙 기반 추천과 기존 점수 계산 구조·가중치를 유지한다.
- LLM은 자연어를 구조화된 조건으로 변환하고, Java가 후보 생성·충돌 검사·점수 계산을 담당한다.
- 기존 Task, Preference, CandidateSlot, Recommendation 및 Controller–Service–Repository 구조를 최대한 재사용한다.
- 기존 API와 현재 HTML/CSS/Vanilla JavaScript 화면을 우선 활용한다.
- 과도한 리팩터링, 새로운 프레임워크·인프라, 범용 스케줄링 엔진, 학습형 추천 등의 기능 확장을 앞세우지 않는다.
- 모델·DTO·DB 변경이 필요하다면, 기존 구조로 해결하기 어려운 이유와 최소 영향 범위를 먼저 확인한다.

## 4. 확정된 추천 정책

이 절은 사용자가 결정한 정책이다. 일부는 T09에서 구현됐으며, 자연어 해석 후속 정책은 아직 미구현이다. 완료 여부는 3장과 개별 구현 보고서로 구분한다.

### 4.1 기존 점수제 유지와 표시 점수 환산

내부 점수는 기존 계산 구조와 가중치를 유지한다.

```text
rawScore = 기본 점수 + 선호 시간대 + 마감 성향 + Task 중요도 + 일정 밀도
displayScore = rawScore / 140.0 × 100
```

- 정렬·적합도 계산 등 내부 판단에 사용하는 원점수는 표시 환산 때문에 변경하지 않는다.
- 사용자에게 보여주는 값만 140점 기준으로 100점 척도로 환산한다.
- 표시 의미는 **추천 적합도**이며, 성공 확률·만족 확률·통계적 신뢰도가 아니다.
- 예: 원점수 70은 표시 50점, 원점수 140은 표시 100점이다.
- 현재 항목별 상한 합은 50 + 30 + 20 + 30 + 10 = 140이다. 이 합은 확률 보정이나 사용자 만족도 검증을 뜻하지 않는다.
- ASAP 방향 오류처럼 확인된 결함은 기존 정책의 의도를 바로잡는 작업으로 다룬다. 이를 임의의 새 가중치나 점수 체계 도입으로 확대하지 않는다.

T09는 UI에서 표시만 소수 첫째 자리로 반올림하며 원점수는 API·DB에 유지한다. 비정상 원점수의 별도 처리 정책은 아직 확정하지 않았다. 잘못된 과거 후보 등으로 점수가 범위를 벗어나는 결함을 표시값 제한으로 숨기지 않는다. 중복 환산으로 내부 점수까지 바뀌지 않도록 검증한다.

### 4.2 후보 생성과 다양성

- 기존 30분 간격 후보 생성을 유지한다.
- 최종 결과가 09:00·09:30·10:00처럼 비슷한 시간에만 집중되지 않도록 다양성을 개선한다.
- T09는 수행 구간 중첩과 날짜·시간 분산을 사용한다. 별도 분 단위 유사도 임계값이나 시간대별 강제 할당은 도입하지 않았다.

### 4.3 원조건과 대안

- 원래 요청한 날짜와 시간대를 우선 추천한다.
- 같은 날짜의 다른 시간을 우선적인 대안으로 고려한다.
- 다른 날짜의 비슷한 선호 시간대도 대안으로 탐색한다.
- **원조건 후보가 존재해도 의미 있는 대안은 함께 제시한다.**
- 원조건 후보가 3개 이상이라는 이유만으로 좋은 대안을 제외하지 않는다. 원조건을 우선하면서 의미 있는 대안도 함께 제시한다.
- 기존 최대 3개 추천 구조를 우선 유지한다.
- 원조건과 대안을 혼동하지 않도록 실제 변경 내용을 설명한다.
- T09는 유효한 원조건 대표와 의미 있는 대안을 선정하고, 선정 후 최종 순위는 기존 원점수순으로 유지한다. 유형별 고정 개수 배분은 하지 않는다.

### 4.4 문구와 기본 노출

| 대상 | 확정 문구·표시 원칙 |
|---|---|
| 실제로 원조건에 정확히 일치하는 후보 | “정확히 일치하는 시간대가 존재해요!” |
| 대안 후보 | “다른 대안도 있어요” |
| 대안 영역 | **접지 않고 기본적으로 표시** |
| 후보별 설명 | 원래 요청에서 무엇을 유지·변경했는지 실제 계산 결과에 맞게 표시 |

부분 시간대 일치나 날짜를 바꾼 대안을 정확 일치로 표시하지 않는다. 기본 Preference가 맞았다는 이유만으로 사용자가 명시한 요청과 정확히 일치했다고 설명하지 않는다. 조건 미지정은 기존 GENERAL 판정을 유지하고, 현재 모델로 표현할 수 없는 조건의 안내는 확정 자연어 정책과 후속 구현 기준을 따른다.

### 4.5 날짜와 반드시 지킬 조건

- 날짜 미지정 시 오늘부터 최대 2주 동안 탐색한다.
- 특정 날짜를 지정했다면 해당 날짜를 최우선으로 추천한다.
- 별도 제한이 없다면 다른 날짜도 최대 2주 범위에서 대안으로 탐색한다.
- 특정 선호 날짜 D의 대안은 D~D+13일이다. 명시적 허용 기간·마감·필수 조건과 교차 적용한다. 날짜 미지정은 오늘~오늘+13일이다.
- 단독 요일의 특정 날짜화, 이번 주 허용 기간, 밤 01:00, 다음 주 날짜 계산은 [확정 자연어 정책](llm-natural-language-policy.md)을 따른다. 이 해석 연결은 후속 구현 대상이다.
- 사용자가 명시한 마감일·허용 기간·필수 조건은 반드시 준수한다.
- 새로운 날짜를 탐색한다면 그 날짜의 수업·기존 Task·Calendar 충돌도 확인해야 한다.

### 4.6 추천 생성과 실제 일정 등록 분리

```text
자연어 입력 → Task 생성 → 추천 후보 생성·제시
→ 사용자가 직접 후보 선택 → 최신 조건 검증 → Calendar 등록
```

추천을 생성했다는 이유만으로 Task를 SCHEDULED로 만들거나 Calendar 이벤트를 생성하지 않는다. 추천 과정의 FreeBusy 조회와 Calendar 이벤트 등록은 다른 작업이다. 실제 이벤트 등록은 사용자가 직접 후보를 선택한 경우에만 수행한다.

### 4.7 Google Calendar 연동 정책 (P01~P04)

아래는 확정된 연동 정책이다. 현재 구현의 완료 여부와 구분하며, 연결 여부와 조회 성공 여부도 서로 다른 상태로 다룬다.

| ID | 확정 정책 |
|---|---|
| P01 | **Google Calendar 미연동 상태에서도 일정 추천은 가능하다.** 이때 Google 일정은 충돌 검사에서 제외되며, 사용자에게 Google 일정이 반영되지 않았음을 명확하게 안내한다. |
| P02 | **추천 후보 선택 및 최종 확정에는 Google Calendar 연결이 필요하다.** 미연동 사용자는 추천 결과를 확인할 수 있지만 확정할 수 없다. 기존 1학기 구현 정책을 유지한다. |
| P03 | **연결된 상태의 FreeBusy 조회 실패를 일정이 없는 상태로 처리하지 않는다.** 정상적인 빈 일정 응답과 API·응답 오류를 구분하고, 조회 실패를 명확하게 안내하며 검증되지 않은 추천·확정은 차단한다. |
| P04 | **미연동 상태에서 생성한 후보는 Calendar 연결 후 그대로 확정할 수 없다.** Google 일정이 추가로 반영되므로 후보를 다시 생성하거나 최신 조건으로 재검증한 후에만 선택할 수 있다. 연결 성공만으로 기존 후보가 검증된 것으로 표시하지 않는다. |

#### 2026-10-17 당시 확인 범위와 작업 배경

아래 표는 T05·T07·T10 구현 전의 **역사적 점검 기록**이다. 현재 미구현 목록으로 읽지 않는다. 이후 T05·T07·T08·T10의 오류 처리·최신 검증·복구 경로와 회귀 결과는 T09 보고서에 요약되어 있다. 이번 자연어 정책 문서화는 이 안정성 처리를 유지하며 테스트를 재실행하지 않았다.

| 정책 | 현재 코드에서 확인한 범위 | 앞으로 확인·수정할 사항 |
|---|---|---|
| P01 | `CalendarService.getCalendarBusyBlocksOrEmpty()`는 저장된 연결 토큰이 없으면 빈 목록을 반환하며, `RecommendationService.recommend()`는 이 경로로 추천을 생성한다. 미연동 추천 경로는 이미 존재한다. | Google 일정 미반영 안내가 실제 추천 결과와 일치하는지 T05에서 확인하고 필요한 오류·안내 처리를 보완한다. |
| P02 | `RecommendationService.select()`는 상태 변경 전에 `validateCalendarConnected()`를 호출하고, 미연동이면 `GOOGLE_CALENDAR_NOT_CONNECTED`로 차단한다. | 기존 서버 차단을 유지하고 관련 회귀 검증을 수행한다. 미연동 사용자가 결과 확인은 가능하되 확정은 불가능함을 UI에서도 명확하게 표시한다. |
| P03 | `GoogleCalendarClient.getBusyBlocks()`는 `IOException`을 실패 예외로 처리하지만, calendars·요청 Calendar·busy 값 누락 시 빈 목록을 반환하고 Calendar별 오류를 별도로 검사하지 않는다. `select()`에도 최신 FreeBusy 재조회는 없다. | T05에서 정상 빈 결과와 오류·불완전 응답을 구분하고 추천 시 실패 처리를 보완한다. 확정 시 최신 조회·검증과 실패 차단은 T07에 연결한다. 정책 전체가 구현 완료된 상태로 보지 않는다. |
| P04 | `select()`는 현재 연결 여부만 검사하며, 미연동 시 생성한 후보에 대해 연결 후 Google 일정을 다시 반영하는 검증은 수행하지 않는다. | T07·T10에서 재생성 또는 최신 조건 재검증과 UI 상태 처리를 구현·검증한다. 구체적인 저장 방식이나 API 변경은 이번에 확정하지 않는다. |

코드 근거: [CalendarService.getCalendarBusyBlocksOrEmpty()](../src/main/java/me/timetablescheduler/domain/calendar/CalendarService.java), [GoogleCalendarClient.getBusyBlocks()](../src/main/java/me/timetablescheduler/domain/calendar/external/GoogleCalendarClient.java), [RecommendationService.select() 및 연결 검사](../src/main/java/me/timetablescheduler/domain/recommendation/service/RecommendationService.java).

작업 구분은 **T05: P01~P03 기존 구현 확인 및 필요한 오류 처리**, **T07·T10: P04 최신 검증 및 UI 상태 처리**, **T08: 확정 이후 Calendar 동기화 실패·복구**로 한다. T08의 등록 실패 복구와 P03의 조회 실패 차단을 혼동하지 않는다.

## 5. 확정·구현된 세부사항과 채택하지 않은 이전 제안

### 5.1 기존 미확정 항목의 현재 상태

| 항목 | 현재 상태 | 남은 범위 |
|---|---|---|
| Hard/Soft | dateRequired·timeRequired·preferredStartTime 도입 | 자연어 표현을 확정 정책에 따라 연결·평가 |
| Task 모델 | T09 nullable 컬럼 추가, 기존 데이터 의미 보존 | 이번 문서화는 스키마·데이터를 변경하지 않음 |
| 원조건·대안 선정 | 원조건 대표와 대안을 고르고 최종 원점수순 유지 | 새 정규화 조건으로 회귀 확인 |
| 후보 유사도 | 실제 수행 구간 중첩 및 날짜·시간 분산 | 임의 분 단위 임계값 추가하지 않음 |
| 후보 개수 | 최대 3개, 억지로 채우지 않음 | 고정 2+1 배분·추가 후보 API는 채택하지 않음 |
| 날짜 탐색 | 날짜 미지정 오늘~+13일, 특정 선호일 D~D+13일 | 명시 주간·가장 가까운 미래 시각의 해석 연결 |
| 분류·설명 | matchType·reason 저장 | 과거 NULL 이력을 새 Task 조건으로 재분류하지 않음 |
| 표시 점수 | UI에서 140점 기준 환산·소수 첫째 자리 반올림 | 비정상 원점수 처리의 별도 정책은 미확정 |

### 5.2 채택하지 않은 제안과 유지할 원칙

- **대안 점수차 30점 제한은 채택하지 않았다.**
- 대안 영역은 접지 않고 기본적으로 표시한다.
- dateFixed/timeFixed는 도입하지 않았다. 실제 도입 필드는 dateRequired/timeRequired/preferredStartTime이다.
- 매 요청마다 고정 여부를 필수로 묻는 UI는 도입하지 않는다. 활동 누락·모호하거나 모순된 조건에 한해 필요한 확인을 한다.
- 60분 유사도·31일 기간 상한·유형별 고정 개수 배분·범용 조건 모델은 채택하지 않았다. matchType 컬럼은 T09에서 실제 도입했으므로 과거 미채택 제안과 구분한다.
- 여섯 자연어 정책의 의미는 [확정 문서](llm-natural-language-policy.md)로 결정됐다. 원본 LLM과 Java 정규화의 중간 표현 계약·평가 실행 도구는 후속 구현·검증 대상이다.

## 6. 단계별 개선 방향

### 1단계: 실제 결함 재검증 및 수정

기존 감사에서 지적한 문제를 현재 코드와 실행 환경에서 확인한 후, 사용자 데이터·보안·핵심 흐름에 미치는 영향에 따라 우선 처리한다.

| 영역 | 우선 확인할 문제 | 목표 |
|---|---|---|
| 보안·데이터 보존 | DB 재생성 설정, 비밀값 기본값, OAuth state 검증 | 데이터 손실·잘못된 계정 연결 위험 방지 |
| 동시성·추천 확정 | 동일/서로 다른 Task의 확정 경쟁, 후보 생성 후 일정 변경 | 최신 조건 검사와 일관된 예약 상태 |
| Calendar 정합성 | 등록 실패, 응답 유실, 외부 성공 후 DB 실패, 중복 요청 | 불명확한 결과를 성공으로 표시하지 않고 안전하게 복구 |
| 시간 계산 | 과거·이미 지난 후보, 시간대·자정 경계, ASAP 방향 | 실제 미래의 유효한 후보와 의도한 계산 |
| 예외·입력·영속성 | 상위 API 장애와 입력 오류 혼동, FreeBusy 오류, 길이·FK·삭제 문제 | 예측 가능한 오류와 데이터 일관성 |
| 기능 상태 UI | JWT 만료, 분석 실패 후 이전 Task 잔류, 확정 후 상태 미갱신 | 화면과 실제 서버 상태 일치 |

이 표는 수정 후보와 목표이며 모든 항목을 이번 작성 시 재현했거나 수정했다는 뜻이 아니다. 락·revision·멱등성·트랜잭션 분리의 구체 방식도 과거 제안을 그대로 의무화하지 않고 필요한 최소 설계로 정한다.

완료 판단은 단순 서버 기동이 아니라 해당 결함의 회귀 검증과 핵심 사용자 흐름의 안정성으로 한다. 테스트·격리 DB·외부 API stub을 우선 활용하고, 실제 연동 검증은 별도 작업 범위에서 수행한다.

### 2단계: 추천 정확성과 품질 개선

- 이 문서의 확정 정책을 기존 추천 코드에 적용할 최소 변경 범위를 검토한다.
- 이미 구현된 Hard/Soft·후보 선정·유사도 처리를 보존하고, 확정 자연어 정책의 추출·Java 정규화·오류 안내를 연결한다.
- 점수 계산과 30분 후보 생성은 재사용하고, 필요한 탐색·선정·설명 부분을 개선한다.
- 후보 탐색 범위와 Calendar 조회 범위를 일치시키고 최소 간격의 날짜 경계도 확인한다.
- 내부 점수 보존과 표시 점수 환산을 분리한다.
- 원조건·대안 문구와 기본 노출을 위한 최소 기능 UI를 연결한다.
- 새 모델·API·DB 변경은 필요성이 확인된 부분만 적용한다.

완료 판단은 원조건 우선·대안 동시 제시·다양성·필수 조건 준수·표시의 사실성이 함께 충족되는지로 한다. 임의의 세부 개수·임계값을 추가하지 않는다. 실제 LLM 정확도는 기존 Fixture 검증과 분리해 측정한다.

### 3단계: Open Design을 활용한 UI 개선

기존 결함 수정과 추천 정책 개선이 끝난 뒤 진행한다. 현재 화면을 기반으로 정보 배치, 읽기 쉬운 점수·설명, 명확한 행동, 반응형·접근성을 개선한다.

- Open Design은 이후 디자인 작업에 활용할 수단이며, 이번 문서 작성에서 실행한 도구가 아니다.
- 시각 개선 과정에서 추천 정책이나 내부 점수·API 의미를 임의로 바꾸지 않는다.
- 대안 기본 노출과 사용자 선택 후 등록 정책을 유지한다.
- 프런트엔드 기술 교체나 대규모 화면 재구축을 전제하지 않는다.

## 7. 기존 T01~T13 계획과의 관계

T01~T13은 과거 검토의 참고 작업 목록이다. **모든 항목이 필수이거나 과거 상세 설계·작업량이 확정된 것은 아니다.** 실제 결함, 전시 핵심 흐름, 기한과 변경 위험을 기준으로 필요한 범위를 선택·통합한다.

| 참고 작업 | 이번 방향에서의 활용 |
|---|---|
| T01 데이터 보존 | 실제 DB 설정과 데이터 보존 위험을 확인하여 최소 수정 |
| T02 시간·ASAP | 확인된 계산 결함을 먼저 수정하고 날짜 탐색 기준과 연결 |
| T03 인증·분석 UI 상태 | 기존 기능을 잘못 사용하게 하는 상태 불일치 수정 |
| T04 비밀값·OAuth | 실제 보안 위험 재검증 및 필요한 수정 |
| T05 오류·입력·외부 응답 | P01~P03의 기존 구현 확인 및 필요한 오류 처리. 미연동 추천·미반영 안내, 확정 시 연결 필수, FreeBusy 정상 빈 결과와 조회 오류 구분 |
| T06 모델·lifecycle | 조건 변경 시 PROPOSED 무효화와 보호 이력을 유지. T09의 조건 필드·유형 컬럼과 구분 |
| T07 최신 충돌·확정 | 선택 시점 검증과 동시성 문제 해결. P04에 따라 연결 전 생성 후보의 재생성 또는 최신 조건 재검증, 조회 실패 시 확정 차단 |
| T08 Calendar 복구 | 확정 이후 Google Calendar 동기화 실패·복구. 중복·실패·불명 결과를 안전하게 처리할 최소 범위 검토 |
| T09 추천 품질 | 구현된 원조건·대안·다양성·설명·표시 점수 보존. 후속으로 확정 자연어 정책과 실제 LLM 평가 연결 |
| T10 확정 UI | 사용자 선택과 등록 결과를 사실대로 표시. P04에 따라 연결 후 기존 후보의 검증 상태와 재생성·재검증 필요성을 반영 |
| T11 조건·편집·사용성 | 필요한 최소 기능 개선만 선별. 복잡한 매회 확인 UI를 전제하지 않음 |
| T12 회귀 검증 | 선택한 결함 수정·추천 개선에 테스트를 함께 연결 |
| T13 실제 연동 리허설 | 전시 핵심 흐름과 실패 복구 검증. 실행 범위는 별도 결정 |

Open Design 기반 시각 개선은 위 결함·추천 개선 이후 단계로 관리한다. 기존 전체 작업량 추정을 현재 일정의 확정값으로 재사용하지 않는다.

## 8. 구현 전·후 확인 기준

### 구현 전

- 현재 코드의 문제인지, 위험 경로인지, 외부 환경 검증이 필요한지 구분한다.
- 최신 사용자 결정과 이전 제안이 섞이지 않았는지 확인한다.
- 기존 코드·API·Task 필드로 해결할 수 있는 범위를 먼저 살핀다.
- 모델 변경이 필요하다면 이유·영향·기존 데이터 처리부터 설명한다.
- 미확정 정책은 구현 전에 좁히며, 개발 과정에서 임의 상수나 UI 흐름으로 굳히지 않는다.

### 구현 후

- 내부 점수와 가중치가 의도 없이 바뀌지 않고 표시만 140점 기준으로 환산되는가?
- 표시 점수를 확률로 오해하게 만들지 않는가?
- 원조건이 있어도 의미 있는 대안을 함께 제시하고, 대안은 기본 노출되는가?
- 날짜 미지정 2주 탐색과 마감·허용 기간·필수 조건 준수가 동작하는가?
- 원조건 일치·변경 이유가 실제 후보와 일치하는가?
- 새로운 날짜에서도 수업·Task·Calendar와 최소 간격을 검사하는가?
- 미연동 상태에서도 추천 결과를 볼 수 있고, Google 일정 미반영 사실을 안내하며 후보 확정은 차단하는가(P01·P02)?
- 연결된 Calendar의 정상적인 빈 일정과 FreeBusy 조회 오류를 구분하며, 실패 안내와 검증되지 않은 추천·확정 차단이 동작하는가(P03)?
- 미연동 시 생성한 후보를 연결 후 그대로 확정하지 못하며, 재생성 또는 최신 조건 재검증을 거친 경우에만 선택할 수 있는가(P04)?
- 추천 생성만으로 Task 예약이나 Calendar 이벤트 생성이 발생하지 않는가?
- 사용자 선택 시 최신 조건 검증과 실패·중복 요청 처리가 동작하는가?
- 조건 변경·인증 만료·분석 실패·새로고침 후에도 서버와 화면 상태가 일치하는가?

위 항목은 향후 검증 기준이다. 이번 문서 작성으로 구현이나 테스트가 완료된 것은 아니다.

## 9. 문서의 적용 범위

이 문서는 사용자 결정에 따른 2학기 개선 방향의 기준으로 사용한다. 자연어 해석은 2026-10-20 [확정 정책](llm-natural-language-policy.md)이 우선한다. 기존 감사와 초기 정책 문서는 당시의 근거로 보존한다. 후속 작업은 **기존 코드 결함 수정 → 추천 품질 개선 → Open Design UI 개선** 순서를 유지하고, 새 설계의 채택과 실제 구현은 별도 검토·요청에 따라 진행한다.
