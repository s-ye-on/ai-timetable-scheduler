# 2026-10-20 LLM 1차·2차 실측 결과 보관

- 평가 날짜: **2026-10-20 / Asia/Seoul**
- 보관 정리일: 2026-10-21
- 대상: timetable-scheduler 한국어 일정 요청 해석
- 평가 데이터: [Golden Dataset v1](../../../llm-evaluation-golden-dataset.md)의 G01~G40, 총 40문장
- 기준 시각: 각 문장에 지정된 Asia/Seoul 고정 시각
- 실행: 각 문장 1회씩, 각 평가 40회
- 요청 모델: **gpt-4o-mini**
- 확인된 1차 응답 모델: **gpt-4o-mini-2024-07-18**

2차도 같은 요청·응답 모델을 사용했다는 내용은 앞선 채팅의 원본 확인 기록에 근거한다. 이번 ZIP에는 2차 manifest와 cases가 없어 모델·기준 시각·반복 설정을 이 보관본만으로 독립 재검증할 수는 없다.

이 디렉터리는 build 밖에 위치하며 Git에 보관한다. Gradle clean으로 삭제되는 일시 실행 산출물과 구분한다. 이번 보관 작업에서는 평가 API를 호출하지 않았다.

## 1. 출처와 확보 상태

사용자가 제공한 llm_evaluation_2026-10-20.zip을 사용했다. JSON 3개는 ZIP의 바이트를 변경하지 않고 복사했다. 이 README는 출처와 한계를 명확히 하기 위해 새로 작성했다.

| 보관 파일 | 자료의 성격 | 검증 범위 |
|---|---|---|
| [baseline-cases.json](baseline-cases.json) | ZIP의 설명에 따르면 대화에 첨부한 **1차 원본 cases.json의 사본** | 40개 ID·입력·기준 시각·응답·판정이 있으며 ZIP 멤버와 바이트 동일. 삭제된 실행 폴더의 파일과 직접 바이트 대조한 것은 아님 |
| [baseline-summary.json](baseline-summary.json) | **1차 터미널 JSON 출력에서 복원한 집계** | 원래 summary.json의 공백·포맷까지 보존한 원본 복제본은 아님. 1차 cases의 주요 집계와 일치 확인 |
| [improved-summary.json](improved-summary.json) | **2차 터미널 JSON 출력에서 복원한 집계** | 2차 원본 summary.json의 바이트 복제본은 아님. JSON·건수·집계 내부 계산 확인. 문장별 원본과의 재집계는 불가 |

복원된 summary를 원본 manifest나 완전한 실행 백업으로 취급하지 않는다. 없는 데이터를 채우거나 정답·실제값을 추측하여 새로 생성하지 않았다.

## 2. 평가 실행과 프롬프트 개선

| 구분 | 실행 ID | 상태 |
|---|---|---|
| 1차 baseline | 20261020-143411-450eb280 | 프롬프트 개선 전 |
| 2차 improved | 20261020-172020-942183aa | 프롬프트 개선 후 |

프롬프트 개선 커밋은 39c27e9(fix(llm): 시간 필수 조건 및 활동명 해석 개선)이다.

- 정확한 시각을 말한 사실과 timeRequired를 분리했다. 일반 요청·선호는 false, 명시적인 시간 필수 조건은 true로 설명했다.
- 날짜와 시간의 필수 여부를 각각 판단하도록 명확히 했다.
- 공부·과제처럼 포괄적인 활동도 유효한 제목으로 인정하고, 활동 자체가 없는 요청과 구분했다.
- 날짜·시간 미지정 활동 요청을 허용하면서 모호한 오전·오후 확인 정책을 유지했다.
- 위 차이를 보여주는 14필드 대조 예시 6개를 추가했다.

개선 당시 모델·Structured Outputs 스키마·Java 파서·추천 점수식·DB·Calendar·UI와 Golden 정답은 변경하지 않았다. 저장된 응답이 프롬프트 예시와 같아야 한다는 뜻은 아니며, Golden 정답은 모델 응답과 독립적으로 정의했다.

## 3. 개선 전후 집계

아래 수치는 보관된 summary에 있는 평가 결과다. 새 API 실행이나 임의 재채점으로 만든 수치가 아니다.

| 지표 | 1차 | 2차 |
|---|---:|---:|
| LLM 원본 전체 일치율 | 1/40, **2.5%** | 20/40, **50.0%** |
| Java 정규화·검증 후 전체 일치율 | 9/40, **22.5%** | 33/40, **82.5%** |
| JSON 스키마 준수 | 40/40, 100% | 40/40, 100% |
| DTO 변환 | 40/40, 100% | 40/40, 100% |
| 원본 timeRequired 필드 일치 | 12/40, 30.0% | 40/40, 100% |
| 원본 title 필드 일치 | 27/40, 67.5% | 40/40, 100% |
| 중대 오류가 표시된 문장 | 10개 | 12개 |

- 전체 일치는 해당 문장의 모든 평가 항목이 통과한 비율이며 필드별 일치율과 다르다.
- MANUAL·ERROR·NOT_EVALUATED를 정답으로 세지 않는다. Golden이 지정한 EXCLUDED만 해당 의미 항목의 분모에서 제외한다.
- 중대 오류 개수는 현재 평가기의 탐지 규칙으로 표시된 **문장 수**다. 전체 실제 위험의 개수나 오류 표시 총합과 동일하지 않으며, 안전성 개선을 이 수치만으로 판단하지 않는다.
- Java 결과 일치율은 정규화·검증과 Task 객체 생성 가능성의 Golden 일치율이다. **실제 일정 추천·DB 저장·Google Calendar 등록 성공률이 아니다.**
- 동일 40개 표본을 각 1회 실행한 비교다. 일반 사용자 요청 전체의 정확도나 반복 실행의 안정성을 입증하지 않는다.

## 4. 미확보 자료와 한계

- **2차 cases.json은 미확보**다. improved-cases.json이나 대체 문장별 결과를 생성하지 않았다.
- 양쪽 실행의 원본 manifest.json, CSV, cases.jsonl은 이 ZIP에 없어 보관하지 않았다.
- 1차 cases에 들어 있는 문장별 모델·프롬프트·스키마 해시는 그대로 보존했다. 2차의 해당 메타데이터 원본은 미확보다.
- 따라서 2차 실패 문장의 실제 JSON이나 모델 메타데이터를 이 디렉터리의 파일만으로 재검증할 수 없다.
- 이 보관본은 확보된 평가 근거의 영구 보관이며, 삭제된 두 실행 폴더 전체를 복구한 것이 아니다.

향후 실제 평가 결과는 clean 전에 build 밖으로 별도 보관해야 한다. API 키·토큰·개인정보가 없는지 검사한 뒤 필요한 산출물만 Git에 포함한다.
