- 작성일: 2026-10-24
- 상태: M1~M3 완료 / M4~M7 미착수
- 계획 수립 기준: `b930bdf` — 수업별 색상 DB 저장 구현까지. 이후 구현 상태는 진행 기록을 참조한다.

## 2. 유지할 사용자 흐름과 디자인

### 사용자 흐름

- 신규: 회원가입 → 자동 로그인 → 수업 등록(선택) → 선호 설정(선택) → Google Calendar 연결(선택) → 홈
- 기존: 로그인 → 홈 → 기존 시간표·선호·Task 조회 → 필요한 관리 또는 새 일정 추천
- 추천: 자연어 분석·Task 저장 → 추천 생성 → 후보 비교·임시 선택 → 명시적 최종 등록 → 결과 확인·필요 시 복구
- 작업 복원: 홈의 확정 일정 또는 추천 화면의 저장한 할 일 → Task·추천 이력 재조회 → 현재 상태에 맞춰 재개

신규 사용자 판단은 실제 회원가입 성공이라는 사건을 기준으로 한다. 수업이 없거나 기본 선호를 사용한다는 이유로
기존 사용자를 온보딩으로 보내지 않는다. 모든 설정을 건너뛰어도 홈과 추천을 이용할 수 있어야 한다.
온보딩을 여러 기기에서 자동 동기화하는 신규 기능·서버 필드는 이번 범위가 아니다.

### 원본 보존

- PC·모바일 레이아웃, 폰트, 색상, 여백, 수업 블록·요일별 목록·버튼·모달 디자인을 최대한 그대로 유지한다.
- 모바일의 요일 선택, 전체 시간표 진입·홈 복귀 위치와 키보드 초점 처리를 보존한다.
- 실제 API 연결에 필요한 문구·검증·상태 표현만 바로잡는다. 임의 재디자인이나 새로운 UI 프레임워크 전환은 하지 않는다.
- 원본의 예시 사용자·고정 날짜·모의 인증·추천·등록 및 API 미연결 안내는 실제 서버 데이터와 상태로 교체한다.
- 원본 CSS 적용 범위를 구분해 기존 로그인·회원가입 스타일이 변하지 않도록 한다. 로컬 폰트를 재사용한다.

10색 식별자는 `BLUE, MINT, PEACH, LAVENDER, ROSE, LEMON, LIME, AQUA, APRICOT, SLATE`다.
서버 enum을 원본 `color-blue` 등의 CSS 팔레트에 명시적으로 매핑한다. 과목명으로 색상을 새로 정하거나 강제로 통일하지 않는다.
범례는 가짜 과목 대신 실제 슬롯의 과목명·색상 조합을 사용한다.

## 3. React 구조·라우팅·상태 관리

### 기본 구조

기존 React·Vite·TypeScript와 CSS를 유지한다. 별도 라우팅·전역 상태 라이브러리는 우선 추가하지 않는다.
아래는 책임 구분이다. 앱 라우팅·AppShell·인증 연결은 M1, 시간표 관리는 M2에서 구현했다. 다른 도메인 화면은 후속 단계에서 구성한다.

| 영역 | 책임 |
|---|---|
| 앱 라우팅·인증 경계 | 공개 인증 화면과 보호된 앱 구분, 현재 경로·복귀 위치, 인증 확인·만료 처리 |
| AppShell | PC 사이드바, 모바일 상단바, 프로필 메뉴, 콘텐츠·공통 알림 영역 |
| 기존 auth 기능 | 로그인·회원가입·JWT 저장·갱신 재사용, 서버 로그아웃과 공통 인증 상태 연결 |
| timetable 기능 | 조회·등록·수정·삭제, 주간표·모바일 목록, 수업 상세·색상·범례 |
| preference·calendar 기능 | 선호 폼의 온보딩/일반 관리 문맥, 연결 시작·상태 확인 |
| planner 기능 | 자연어 입력, 분석 조건, 저장한 할 일, 추천 후보, 최종 등록·복구 |
| 공통 UI | 원본 스타일의 버튼·로딩·빈 상태·오류 안내·모달·토스트 |

기능별 컴포넌트·hooks·API 모듈로 나누되 기존 AuthClient와 갱신 처리를 중복 구현하지 않는다.

### 경로

| 경로 | 용도 |
|---|---|
| `/login`, `/signup` | 현재 인증 화면 유지 |
| `/#home` | 보호된 홈 |
| `/#planner?taskId=123` | 일정 추천·해당 Task 작업 복원 |
| `/#timetable` | 시간표 관리 |
| `/#onboarding/1`, `/2`, `/3` | 수업 → 선호 → Calendar의 선택적 초기 설정 |
| `/#onboarding/2?mode=manage&returnTo=home` | 같은 선호 폼의 일반 관리 진입·복귀 |

`/2`, `/3`은 각각 `/#onboarding/2`, `/#onboarding/3`의 축약 표기다.
일반 설정의 진입 문맥은 URL에 남겨 새로고침 후에도 온보딩 저장 동작으로 바뀌지 않게 한다.
복귀 목적지는 앱 내부 허용 경로만 사용한다. hash 변경·뒤로 가기·직접 진입에 맞춰 화면·초점·스크롤을 복원한다.
아직 선언만 된 가입 온보딩 목적지는 M7에서 위 경로와 일치시키며, 그 전에는 기존 플래너 목적지를 유지한다.

### 상태 소유권

| 위치 | 보관할 상태 |
|---|---|
| 서버 | 사용자·수업·선호·Task·추천·Calendar 연결·확정·동기화 상태 |
| URL | 화면·온보딩 단계·설정 진입 목적·재개할 Task ID |
| React 로컬 | 입력 초안·임시 선택 후보 ID·모달·로딩/오류·모바일 요일 |
| 필요 시 사용자별 보조 저장 | 입력 초안·마지막 Task ID·최소 진행 정보. 서버 상태의 대체물이 아님 |

프로토타입의 전체 state localStorage 저장 방식은 이식하지 않는다. 보조 저장은 사용자 ID별로 분리하고,
로그아웃·사용자 전환 시 정리한다. 복원은 Task 소유권·후보·최신 상태를 서버에서 확인한 뒤 수행한다.
늦게 도착한 분석·조회 응답이 새 입력·다른 Task·새 사용자 화면을 덮지 않도록 한다.

## 4. 기존 Spring Boot API 연결

새 API를 만들기보다 다음 계약을 재사용한다. 아래 경로는 프론트 화면 경로가 아닌 실제 서버 API다.

| 기능 | 기존 API | 주요 데이터·처리 |
|---|---|---|
| 인증 | `POST /api/auth/login`, `POST /api/auth/register`, `GET /api/auth/me`, `POST /api/auth/refresh`, `POST /api/auth/logout` | 현재 인증·자동 로그인 재사용. 사용자 조회와 갱신 실패·로그아웃 연결 |
| 시간표 | `GET/POST /timetable-slots`, `GET/PUT/DELETE /timetable-slots/{id}` | `subjectName, dayOfWeek, location, startTime, endTime, color`와 슬롯 ID |
| 선호 | `GET/PUT/DELETE /preferences` | 시간대·가용 시간·최소 여유·밀도·마감 성향·`customized`; DELETE는 기본값 복원 |
| Calendar | `GET /api/calendar/oauth/url`, `GET /api/calendar/status` | 인증 URL 시작, `{connected}` 재조회. callback은 기존 백엔드 유지 |
| 분석·Task 저장 | `POST /tasks/natural-language` | `{message}` 최대 500자. 성공 응답의 Task ID·구조화 조건·상태 사용 |
| Task 조회·복원 | `GET /tasks`, `GET /tasks/{id}` | 요청 조건·설명·상태·`scheduledStartAt/EndAt` |
| 추천 | `POST/GET /tasks/{id}/recommendations` | 생성은 `message, recommendations`; 후보는 시각·rank·score·reason·status·matchType·syncRetryable |
| 추천 이력 | `GET /tasks/{id}/recommendations?includeHistory=true` | 전체 이력에서 선택·동기화 상태 복원. 활성 후보 순위와 이력 순서를 구분 |
| 최종 확정·동기화 복구 | `POST /recommendations/{id}/select` | 최신 검증·Task 확정·Google 등록까지 처리. 별도 임시 선택 API나 새 retry API를 가정하지 않음 |

- 홈의 확정 일정은 `SCHEDULED`, 저장한 미확정 할 일은 `UNSCHEDULED`를 기준으로 구분한다. `COMPLETED/CANCELED`를 미확정으로 뭉뚱그리지 않는다.
- Task만으로 확정 시간은 표시할 수 있지만 Google 동기화 상세는 추천 이력이 필요하다. 확인 전에는 완료 배지를 표시하지 않는다.
- 필요한 일정·상세의 이력을 조회하고 결과를 재사용해 중복 호출을 줄인다. 홈용 신규 일괄 API는 우선 추가하지 않는다.
- 선호 값은 원본 `ANY→ANYTIME`, `EARLY→ASAP`, `LATE→NEAR_DEADLINE`로 명시적으로 변환한다.
- 여유 시간은 서버 기준인 0 이상·5분 단위로 검증한다. 원본의 1분 단위·최대 120분 제한을 임의의 서비스 정책으로 가져오지 않는다.
- 공통 요청 계층은 기존 JWT 처리를 유지하면서 오류의 `status/code/fieldErrors`를 보존하고, 기능별 안전한 안내로 연결한다.

- [ ] 추천 화면에 저장한 미확정 Task 목록을 연결하고 Task·추천 이력을 재조회해 작업을 복원한다.

**완료 조건**
- [ ] 신규 계정에 예시 수업·Task를 넣지 않고 기존 사용자를 반복 온보딩시키지 않는다.
- [ ] 확정 여부와 Google 동기화 완료 여부를 구분한다. 조회 실패는 빈 목록으로 바꾸지 않는다.

**검증 기준**
- [ ] 신규/기존 계정, 빈 상태·조회 실패, Task 전환·삭제된 Task·소유권 오류·뒤로 가기·새로고침을 확인한다.
- [ ] 늦은 응답과 사용자 전환이 다른 사용자의 데이터나 이전 Task를 복원하지 않는지 확인한다.

### M5. 자연어 분석·추천

**작업 범위**
- [ ] 실제 자연어 분석·Task 저장과 별도 추천 생성을 연결한다.
- [ ] Task의 필수/선호·정확한 시각·기간·마감 조건, 추천 유형·이유·확인된 제외 사유를 표시한다.
- [ ] 적합도만 140점 기준 100점 척도로 표시하고 원점수·서버 rank는 내부 처리에 유지한다.

**완료 조건**
- [ ] 분석·추천만으로 일정을 확정하지 않는다. 실패·입력 변경 후 이전 결과로 잘못된 요청을 보내지 않는다.
- [ ] 실제 matchType으로 원조건/대안을 표시하고 대안은 기본 펼침으로 제공한다. 억지 개수·재정렬을 추가하지 않는다.

**검증 기준**
- [ ] 날짜 미지정·필수/선호·정확한 시각·지원 상대 시각, 분석 실패·확인 요청·추천 없음·외부 조회 실패를 검증한다.
- [ ] 원조건 0/1/여러 개, GENERAL·이전 후보·legacy null 조건 표시와 새로고침 후 순위 복원을 확인한다.
- [ ] 화면과 도움말에서 내부 원점수를 노출하지 않는지 확인한다.

### M6. 최종 등록·실패 복구

**작업 범위**
- [ ] 후보 선택은 로컬 상태로 두고 명시적 최종 등록 버튼에서만 `/select`를 호출한다.
- [ ] T07 최신 충돌 검증과 T08 동일 후보 동기화 재시도를 기존 API로 연결한다.
- [ ] 확정·동기화 실패·수동 확인 필요·응답 유실 상태를 구분하고 재조회·복구 행동을 제공한다.

**완료 조건**
- [ ] 사용자 최종 동의 전 등록 요청이 없고 처리 중 중복 제출을 막는다.
- [ ] 미연동 상태에서는 확정하지 않는다. 연결 후 기존 후보를 검증 완료로 표시하지 않는다.
- [ ] SYNCED 확인 후에만 등록 완료를 표시하며 재시도는 서버의 syncRetryable과 실제 상태를 따른다.

**검증 기준**
- [ ] 최신 일정 충돌·과거 후보·연결 전 생성 후보·FreeBusy 실패·중복 클릭을 확인한다.
- [ ] 동기화 실패·재시도 가능/불가·응답 유실·상태 조회 실패·재로그인 및 새로고침 복원을 확인한다.
- [ ] 불명확한 결과를 무조건 재등록하거나 새 후보 생성으로 우회하지 않는지 확인한다.

### M7. 통합 검증·진입 전환

**작업 범위**
- [ ] M1~M6를 연결해 신규·기존 사용자와 정상·실패 복구 흐름을 통합 검증한다.
- [ ] 검증 후 로그인은 React 홈, 회원가입은 React 온보딩으로 목적지 상수를 변경한다.
- [ ] 실제 실행·배포의 정적 경로·SPA 접근·백엔드 프록시 연결을 확인한다.

**완료 조건**
- [ ] 신규 가입부터 선택적 설정·추천·명시적 최종 등록·결과 재조회까지 흐름이 이어진다.
- [ ] 기존 사용자는 홈에서 시작하며 관리 후 복귀·Task 재개·인증 만료 복구가 가능하다.
- [ ] 기존 백엔드 정책과 로그인·회원가입 디자인을 보존한 채 진입을 전환한다.

**검증 기준**

- [ ] 관련 프론트 테스트·빌드와 전체 Java 회귀 테스트 결과를 기록한다. 테스트 삭제·비활성화·검증 약화로 통과시키지 않는다.
- [ ] 격리 DB·외부 API Stub의 전체 흐름 검증과 실제 외부 연동 확인 여부를 분리해 기록한다.
- [ ] 실제 OpenAI·Google API 검증은 수행 여부와 허용 범위를 명시하고 실행하지 않은 항목을 통과로 표시하지 않는다.

## 6. 유지해야 할 안전 정책

- 인증 복원이 끝나기 전 보호된 데이터를 표시하지 않는다. 토큰·비밀번호·Secret을 로그나 화면에 노출하지 않는다.
- Google Calendar 연결은 선택이다. 미연동 추천에는 Google 일정 미반영을 안내한다(P01).
- 실제 추천 확정에는 Calendar 연결이 필요하다(P02). 내부 일정만 따로 확정하는 흐름을 추가하지 않는다.
- 연결된 Calendar의 FreeBusy 실패는 빈 일정과 구분하고 검증되지 않은 추천·신규 확정을 차단한다(P03).
- 연결 전 생성한 후보도 연결 후 최신 검증을 통과해야 한다(P04). 연결 배지는 후보 검증 완료 배지가 아니다.
- `POST /recommendations/{id}/select`는 확정·Google 등록을 함께 수행한다. UI 임시 선택과 혼동하지 않는다.
- Task가 SCHEDULED여도 Google 등록 완료는 아닐 수 있다. SELECTED/SYNC_FAILED는 확인·복구 대상으로 구분한다.
- syncRetryable이 허용하는 동일 후보·동일 API로 복구하고, 불확실한 결과는 먼저 조회한다. T08 멱등성을 우회하지 않는다.
- 기존 Java 점수식·가중치·후보 생성·최종 순위·LLM/Java 책임 분리·데이터 보존 정책을 유지한다.

## 8. 진행 상태 갱신 방법

각 단계 작업 시 이 문서에서 다음을 함께 갱신한다.

1. 현황 표의 상태·완료일·커밋·검증 근거를 갱신한다.
2. 실제 완료·검증한 체크박스만 체크한다. 부분 완료·미검증은 남겨 둔다.
3. API Stub·격리 DB·실제 서비스 검증을 구분하고 테스트 수·실패·미실행 사유를 기록한다.
4. 범위 변경이나 미해결 문제는 기록하되 합의하지 않은 설계·정책을 완료 사항으로 추가하지 않는다.
5. 모든 단계가 DONE이고 통합 검증까지 끝난 뒤에만 전체 상태를 구현 완료로 바꾼다.
