# 시간표 슬롯 색상 저장

## API 계약

기존 `/timetable-slots` 생성·수정·단건 및 목록 조회 API에 `color` 필드를 추가했다.
Controller 경로·인증·사용자 소유권·시간 충돌 검사는 기존과 같다.

- 식별자: `BLUE`, `MINT`, `PEACH`, `LAVENDER`, `ROSE`, `LEMON`, `LIME`, `AQUA`, `APRICOT`, `SLATE`
- 생성에서 생략 또는 `null`: `BLUE`를 저장한다.
- 수정에서 생략 또는 `null`: 저장된 색상을 유지한다. 명시적인 `BLUE`는 기본색으로 변경한다.
- 대소문자를 구분하며 알 수 없는 값·빈 문자열·숫자·잘못된 JSON 타입은 `INVALID_REQUEST`/HTTP 400이다.
- 단건·목록·생성·수정 응답은 저장된 `color` 식별자를 반환한다.
- 색상은 슬롯 소유 데이터다. 같은 과목명이라도 다른 슬롯의 색상을 바꾸지 않는다.

기존 Java 생성·수정 메서드 및 요청 DTO 생성자도 색상 없는 호출을 지원한다.
React 색상 선택 UI와 HEX 팔레트 매핑은 후속 화면 이식에서 연결한다.

## H2 스키마와 적용 절차

`timetable_slot.color`는 `VARCHAR(16) DEFAULT 'BLUE' NOT NULL`이며 10개 식별자의 CHECK 제약을 둔다.
새 과목 테이블이나 인덱스는 필요하지 않다. 기존 Service 트랜잭션·사용자 락을 재사용한다.

`database.properties`는 `schema-h2.sql` → 기존 T09 SQL → `add-timetable-slot-color.sql` 순으로 실행하고
`ddl-auto=validate`를 유지한다. 신규 DB와 기존 DB 모두 이 경로를 사용한다.

1. 실행 구성의 datasource URL과 작업 디렉터리를 확인해 실제 H2 파일 경로를 확정한다.
2. 서버를 중지하고 DB 파일 점유가 없는지 확인한 뒤 `.mv.db`를 별도 비공개 위치에 백업한다. 백업과 원본의 SHA-256을 비교한다.
3. 신규 격리 DB 및 백업 복제본에서 추가 SQL을 적용하고 반복 실행·재시작·기존 데이터 보존을 확인한다.
4. 서버가 중지된 상태에서 검증된 추가 SQL을 기존 DB에 적용하거나, 검증된 코드의 초기화 경로로 적용한다.
5. `validate` 재시작 및 기존 행·식별자·Google 이벤트 ID 등의 보존을 확인한다.

추가 SQL은 `IF NOT EXISTS`를 사용한다. 최초 추가 시 기존 행에 BLUE를 적용하고,
반복 실행에서는 이미 선택된 색상을 덮지 않는다. 전체 행 UPDATE나 데이터 삭제를 수행하지 않는다.
H2 DDL은 자동 커밋되므로 실패하면 중간 스키마 상태를 먼저 확인한다. 백업 복원은 서버 중지 후 별도로 수행한다.
사용자 데이터·토큰이 포함되는 DB 백업과 검증 자료는 Git에 넣지 않는다.

## 검증

- API: 10개 색상 저장·변경·재조회, 생략/null, 잘못된 타입과 식별자, 슬롯 독립성, 타인 접근 차단, 기존 충돌 검사
- 영속성: API 테스트에서 flush/clear 후 재조회, 격리 파일 DB에서 반복 SQL과 `validate` 재시작, 기존 값·선택 색상 보존
- 실제 DB: 중지 후 백업 → 복제본 검증 → 원본 추가 SQL 적용 → 기존 7개 테이블의 기존 열 데이터 해시 비교 및 재시작
- 추천 알고리즘·Calendar·인증은 전체 Java 회귀 테스트로 확인한다. React 코드는 변경하지 않는다.
