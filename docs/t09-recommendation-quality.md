# T09 구현 및 검증 결과

> 이 문서는 2026-10-19 T09 구현·Fixture 실행 기록이다. 2026-10-20 확정된 [LLM 자연어 해석 정책](llm-natural-language-policy.md)은 확정 당시 별도 후속 구현 대상이었다. 아래 과거 결과를 새 정책의 구현·실제 LLM 평가 완료로 해석하지 않는다.

> **2026-10-20 후속 구현 반영:** 확정된 6개 자연어 정책의 Java 정규화·오류 처리를 구현하고 Java 427개·UI 29개 회귀를 통과했다. 아래 이전의 “후속 구현 대상/미구현”은 당시 점검 기록이며, 최신 완료 범위와 남은 실제 LLM 평가는 [자연어 정책의 후속 구현 결과](llm-natural-language-policy.md#후속-구현-결과-2026-10-20)를 따른다. 과거 Fixture 표·점수·테스트 기록은 변경하지 않았다.

## 1. 변경 목적과 경계

기존 엔진은 날짜를 제한 조건으로만 해석하고 정확한 시작 시각을 저장하지 못했다. 같은 날짜의 30분 차이 후보가 상위 세 자리를 차지할 수 있었고, 날짜 미지정 요청은 추천할 수 없었다.

T09는 LLM → Task → 후보 생성 → 사용자 선택이라는 구조를 유지하면서 요청 의도를 저장하고, 후보 집합을 넓힌 뒤 대표를 선정한다. LLM은 구조화만 담당하고 Java가 날짜·시간·충돌·점수·선정을 결정한다. 기존 점수 공식과 가중치, 원점수 최종 내림차순 정렬, Controller–Service–Repository, T07 사용자 단위 DB 락, T08 이벤트 조회 우선 복구, T10 상태 복원을 유지했다.

새 인프라나 범용 조건 엔진은 추가하지 않았다. 요청 조건 세 필드와 저장된 추천 유형이 필요하므로 DTO·Entity·DB를 함께 변경했다. 변경 파일 수를 줄이기 위해 정확 시각이나 데이터 보존 요구사항을 생략하지 않았다.

## 2. 자연어 구조화와 API

### 이전과 이후 JSON

아래는 **실제 OpenAI 응답이 아니라 테스트에 공급한 구조화 Fixture의 예시**다. 기준일은 2026-10-19이고, 첫 요청은 “목요일 저녁 7시에 알고리즘 공부 2시간”이다.

당시 Fixture는 `preferredDayOfWeek=THURSDAY`를 직접 넣었다. 확정된 G01은 Java 정규화 후 `preferredDate=2026-10-22`, `preferredDayOfWeek=null`이어야 한다. 다음 JSON은 당시 구현 검증용 입력을 보존한 것으로 최신 Golden 정답이 아니다.

이전 계약으로 표현할 수 있었던 값:

```json
{
  "title": "알고리즘",
  "category": "STUDY",
  "durationMinutes": 120,
  "preferredDate": null,
  "preferredDayOfWeek": "THURSDAY",
  "preferredDateRange": null,
  "preferredTimeRange": "EVENING",
  "deadline": null,
  "priority": "NORMAL",
  "description": "목요일 저녁 7시에 알고리즘 공부 2시간"
}
```

19:00과 필수·선호의 차이는 위 계약에 저장되지 않았다. 개선 계약은 다음과 같다.

```json
{
  "title": "알고리즘",
  "category": "STUDY",
  "durationMinutes": 120,
  "preferredDate": null,
  "preferredDayOfWeek": "THURSDAY",
  "preferredDateRange": null,
  "preferredTimeRange": "EVENING",
  "deadline": null,
  "priority": "NORMAL",
  "description": "목요일 저녁 7시에 알고리즘 공부 2시간",
  "dateRequired": false,
  "timeRequired": false,
  "preferredStartTime": "19:00",
  "clarificationReason": null
}
```

Structured Outputs는 모든 키를 required로 선언하고 값이 없을 때 nullable로 반환한다. 객체의 `additionalProperties`는 false다. `clarificationReason`은 LLM 경계에서만 사용하며 Task 컬럼으로 저장하지 않는다.

### 필드 의미와 검증

| 필드 | 의미 | Java 검증·처리 |
|---|---|---|
| `dateRequired` | 지정 날짜·요일이 필수인지 | true이면 날짜·요일이 필요하고 날짜 탐색을 제한한다. false이면 해당 날짜·요일을 원조건으로 분류하되 대안을 허용한다. |
| `timeRequired` | 지정 시각·시간대가 필수인지 | true이고 정확 시각이 있으면 그 시작만 허용한다. 정확 시각이 없으면 지정 밴드에 전체 소요 시간이 들어가야 한다. |
| `preferredStartTime` | 목표 시작 HH:mm | 초·소수 초를 거절한다. 지정 밴드와 시작 시각 자체가 모순되면 거절한다. 필수 정확 시각은 밴드 전체 포함보다 우선하지만 가점 조건은 기존대로다. |
| `preferredDateRange` | 명시적인 허용 기간 | 날짜·요일 선호와 공존할 수 있다. 순서, 마감일, 필수 날짜와의 모순을 검사한다. |
| `clarificationReason` | 모호·지원 불가 조건 | 현재는 값이 있으면 `LLM_CLARIFICATION_REQUIRED`로 먼저 중단한다. 확정 G02/G05는 활동 누락을 `MISSING_LLM_TITLE` / 400과 지정 문구로 구분해야 하며 이 분류 보완은 미구현이다. |

새 LLM 응답에서 두 필수 여부가 누락되면 임의로 false 처리하지 않는다. 원문에 드러난 시각 유실·변경, 오전/오후 없는 “7시”, 복수의 다른 시작 시각, 일부 표현 불가 조건도 추가 검증한다. “19:10”과 “오후 7:10”, “저녁 일곱시부터”는 정상 시각과 비교한다. 이 검증은 제한된 표현에 대한 방어 장치이며 자연어 전체의 의미를 증명하는 기능은 아니다.

기존 저장 데이터의 NULL은 유지한다. 날짜 NULL 플래그는 기존 날짜 제한, 시간 NULL 플래그는 기존 밴드 가점 의미다. 기존 Task 수정 API에서 새 값을 생략하면 저장값을 유지한다. 정확 시각을 지우려면 `clearPreferredStartTime=true`를 사용한다. 삭제 플래그와 새 시각의 동시 지정은 거절한다. 조건 수정 시 T06처럼 PROPOSED 후보를 만료한다.

### 날짜·충돌·선정

- 날짜 미지정: 오늘부터 14일. 요일 선호만 있으면 같은 기간에서 해당 요일을 원조건으로 분류한다.
- 특정 선호 날짜: D부터 D+13일. 시간이 지나도 D를 오늘로 재설정하지 않는다.
- 필수 날짜·요일, 명시 허용 기간, 마감일을 교차 적용한다. 명시된 기간만 있는 기존 요청은 그 기간을 유지한다.
- 사용 가능 시간, 정확한 소요 시간, 미래 시각, 필수 조건을 모든 시작 후보에 동일하게 적용한다.
- 수업·확정 Task·Calendar의 충돌에 최소 여유 시간을 적용한다. Calendar 조회는 실제 탐색 날짜 전체의 첫날 00:00에서 여유 시간을 빼고, 마지막 다음 날 00:00에 여유 시간을 더한다. 인접 날짜 수업·일정도 검사한다.
- 밀도 가점의 기존 당일 입력·계산은 그대로 유지한다. 충돌 검사의 인접 날짜 확대와 점수 변경을 섞지 않는다.
- 유효 EXACT의 최고 원점수 대표를 확보한다. 같은 실제 날짜의 TIME_CHANGED 대안을 먼저 검토하고, 없으면 날짜 변경 대안을 검토한다.
- 남는 자리는 고정 유형 할당 없이 이미 선택한 날짜와 다른 날짜, 원점수, 변경 축, 날짜·시간 분산을 고려한다. 같은 날짜에서 서로 겹치는 수행 구간은 중복에 가까운 선택으로 제외한다. 임의의 “몇 분 이상” 또는 “30점 이내” 제한은 없다.
- 최대 세 개이며 필수 조건 때문에 하나만 가능하면 하나만 반환한다. 마지막에는 선정된 집합을 기존 원점수 내림차순 및 안정 정렬 순서로 복원한다.

**원조건 대표 포함과 최종 1위 보장은 다르다.** 기존 가중치·정렬을 유지했으므로 더 이른 대안이 더 높은 원점수를 받으면 원조건보다 위에 표시될 수 있다.

이는 당시 후보 집합에 대한 설명이다. 새 G01/G04는 단독 요일을 특정 날짜 D로 정규화하므로 D 이전 후보를 탐색하지 않는다. 아래 월요일 대안 결과는 변경 후의 기대 결과가 아니다. 선정된 집합의 최종 원점수순 정책은 유지한다.

기본 50 + 기존 시간대 가점 + 마감 성향 가점 + 중요도 가점 + 밀도 가점은 바꾸지 않았다. 예제의 목요일 19시 후보는 50 + EVENING 30 + NORMAL 9 + BALANCED 0 = 89점이다. 마감일이 없어 마감 성향 가점은 없다. 표시만 `round(원점수 / 140 × 100, 1)`이며 확률이 아니다.

### 저장 유형과 UI

`EXACT`, `TIME_CHANGED`, `DATE_CHANGED`, `DATE_AND_TIME_CHANGED`, `GENERAL`을 저장한다. 정확 시각이 있으면 밴드만 맞는 후보를 EXACT라고 부르지 않는다. 사용자 요청에 날짜·시간이 없으면 Preference가 맞더라도 GENERAL이다.

EXACT에만 “정확히 일치하는 시간대가 존재해요!”를 표시하고 변경 유형에는 “다른 대안도 있어요”와 변경 내용을 표시한다. 대안은 접지 않는다. 서버 이유는 HTML 이스케이프해 표시한다. 과거 NULL 유형은 현재 Task를 보고 재분류하지 않는다.

P01~P04를 유지한다. 미연동 추천은 가능하지만 확정은 차단한다. 연결됐으나 조회가 실패하면 빈 일정으로 간주하지 않는다. 연결 전 후보도 선택 시 최신 조건으로 검사한다. 추천 생성은 Task 확정이나 Calendar 이벤트 생성을 수행하지 않는다.

## 4. 당시 실제 엔진을 실행한 개선 전후 비교

아래 결과는 **실제 외부 LLM/Calendar E2E 결과가 아니라 고정된 구조화 Fixture를 실제 Java 정책·선정 코드로 처리한 테스트 실행 결과**다. 기준은 2026-10-19 월요일 08:00 Asia/Seoul, 가능 시간 09:00~22:00, 여유 0분, 빈 수업·기존 일정·Calendar, NORMAL, BALANCED, ANYTIME, 마감 없음이다. 실제 사용자 데이터는 사용하지 않았다.

이전 비교는 T10 기준 `784aaf6`의 RecommendationPolicy를 임시 디렉터리에서 별도 클래스로 실행했다. 현재 Task Fixture를 넣은 **엔진 비교**이며 이전 전체 LLM/API를 재기동한 결과는 아니다.

### ① 목요일 저녁 7시에 알고리즘 공부 2시간

구조화: THURSDAY / EVENING / 19:00 / 120분 / 필수 여부 false·false.

이전: 목요일 18:00~20:00, 18:30~20:30, 19:00~21:00(각 89점). 정확 시각을 표현할 필드가 없었다.

| 개선 후 순위 | 시간 | 유형 | 원점수 / 표시 적합도 |
|---|---|---|---|
| 1 | 10/19 월 19:00~21:00 | DATE_CHANGED | 95 / 67.9 |
| 2 | 10/22 목 19:00~21:00 | EXACT | 89 / 63.6 |
| 3 | 10/22 목 17:00~19:00 | TIME_CHANGED | 59 / 42.1 |

원조건은 정확한 시작을 보존한다. 첫 대안은 시간을 유지하고 날짜를, 두 번째는 날짜를 유지하고 시간을 바꾼다. 겹치는 18:30 등은 대표 구간 중복으로 최종 집합에서 빠진다. 17시 후보는 EVENING 전체 포함 가점을 받지 않는다.

### ② 반드시 목요일 7시에만 가능해

이 입력은 오전·오후가 없는 모호한 사례이며 새 Golden ID G03에 해당한다. **G02의 “반드시 목요일 저녁 7시에만 가능해”와 다르다.** 새 G02는 시각 모호함이 아니라 활동 누락으로 중단해야 한다.

“7시”의 오전·오후가 명확하지 않다. 정상 정책은 `dateRequired=true`, `timeRequired=true`, `preferredStartTime=null`과 확인 필요 사유를 구조화한 뒤 오류로 중단하는 것이다. LLM이 임의의 07:00/19:00을 넣은 Fixture도 원문 검증에서 거절한다. 추천 결과는 **없음**이며 사용자가 오전/오후를 명확히 해야 한다. 임의로 오후 7시 성공 예제로 보고하지 않는다.

별도 명확한 Fixture인 “2026-10-22 19시에만”은 true·true/19:00으로 실행했고 목요일 19:00~21:00 EXACT 하나만 나왔다(89 / 63.6). 이전 모델은 필수 시각을 보존하지 못했다.

### ③ 화요일 점심이면 좋겠어. 안 되면 다른 날도 괜찮아

이 표는 활동·60분을 직접 넣은 정책 Fixture 결과다. 실제 자연어 파서가 활동 없는 문장을 정상 수용했다는 증거가 아니다. 새 G05는 “이번 주 안에” 제한도 있으므로 아래 입력과 같지 않으며, 활동명 누락으로 Task를 생성하지 않는 정답을 사용한다.

구조화: TUESDAY / LUNCH / 정확 시각 null / 60분 Fixture / false·false.

이전: 화요일 12:00~13:00, 12:30~13:30, 13:00~14:00(각 93점).

| 개선 후 순위 | 시간 | 유형 | 원점수 / 표시 적합도 |
|---|---|---|---|
| 1 | 10/19 월 12:00~13:00 | DATE_CHANGED | 95 / 67.9 |
| 2 | 10/20 화 12:00~13:00 | EXACT | 93 / 66.4 |
| 3 | 10/20 화 11:00~12:00 | TIME_CHANGED | 63 / 45.0 |

화요일 정확 후보가 있어도 대안을 찾는다. 원조건 시간대에 전체 소요 시간이 들어가는지 검사하며, 11시 후보에는 점심 가점을 주지 않는다.

### ④ 목요일 19시 10분에 공부하고 싶어

새 G04는 특정 날짜와 자동 추론한 EVENING, 소요 시간 기본값 60분을 사용한다. 아래 요일·120분 Fixture는 과거 실행 기록으로만 보존하고 최신 Golden 결과로 재사용하지 않는다.

구조화: THURSDAY / EVENING / 19:10 / **120분을 지정한 테스트 Fixture** / false·false. 원문에 소요 시간이 없어 실제 파서 기본값은 60분이며 이 표의 120분과 구분해야 한다.

이전: 18:00, 18:30, 19:00 시작(각 89점); 19:10은 표현·생성되지 않았다.

| 개선 후 순위 | 시간 | 유형 | 원점수 / 표시 적합도 |
|---|---|---|---|
| 1 | 10/19 월 19:10~21:10 | DATE_CHANGED | 95 / 67.9 |
| 2 | 10/22 목 19:10~21:10 | EXACT | 89 / 63.6 |
| 3 | 10/22 목 17:00~19:00 | TIME_CHANGED | 59 / 42.1 |

19:10은 추가 후보지만 검증을 우회하지 않는다. 별도 실제 H2/API 통합 테스트에서도 19:10 후보 확정·중복 요청을 실행해 이벤트 생성 한 번과 내부 SYNCED 상태를 검증했다. 이 테스트의 LLM·Calendar는 Stub이다.

### ⑤ 과제할 시간 1시간 추천해 줘

구조화: 날짜·요일·기간·밴드·정확 시각 null / 60분 / false·false.

이전 엔진 후보는 빈 목록이고 이전 입력 검증도 날짜 조건을 요구했다.

| 개선 후 순위 | 시간 | 유형 | 원점수 / 표시 적합도 |
|---|---|---|---|
| 1 | 10/19 월 09:00~10:00 | GENERAL | 65 / 46.4 |
| 2 | 10/20 화 21:00~22:00 | GENERAL | 63 / 45.0 |
| 3 | 10/21 수 21:00~22:00 | GENERAL | 61 / 43.6 |

14일 후보 전체에서 서로 다른 날짜의 대표를 고른 실제 결과다. 같은 점수의 시간 선택에 시간 분산이 작용하므로 매일 아침으로 고정되지 않는다. 개인화 학습이나 시간대별 강제 배분 결과는 아니다.

## 6. 평가와 남은 한계

코드·격리 테스트 범위에서 T09의 요청 의도 저장, 정확 시각, 14일/필수 범위, 원조건·대안, 저장 유형·설명, 표시 점수, 안전한 DB 변경을 구현했다. 기존 안전장치를 우회하지 않는다.

한계는 다음과 같다.

- 실제 LLM 응답 정확도와 실제 Google 계정 E2E는 검증하지 않았다. Structured Outputs와 Java 검증을 통과해도 모든 자연어 의미가 보장되는 것은 아니다.
- 복수 날짜 OR, 날짜 제외, 모호한 허용 기간 등 현재 최소 모델로 표현할 수 없는 요청은 확인 필요로 처리한다. 모든 가능한 표현을 정규식으로 인지할 수는 없다.
- 현재 “밤 한 시”의 시간 비교는 01:00으로 지원하지만 가장 가까운 미래 날짜를 정하는 Java 단계는 없다. 확정 G37은 요청 시작 Clock을 한 번 캡처해 날짜를 계산하도록 요구하며, 이 연결은 후속 구현 대상이다.
- 기존 시간대 가점과 중요도는 휴리스틱이다. 원조건 확보 후 최종 원점수순을 유지하므로 대안이 1위가 될 수 있다. 임의로 점수를 더해 순서를 바꾸지 않았다.
- 비슷함은 수행 구간 중첩과 날짜·시간 분산으로 판단한다. 30분짜리 작업의 인접한 비중첩 후보까지 모두 금지하는 정책은 추가하지 않았다.
- 사용 가능 시간 범위 밖이나 자정을 넘기는 수행 구간 등 기존 엔진의 일일 수행 범위는 유지했다.
- 다른 개발·배포 DB도 서버 종료·백업·복제 검증 후 적용해야 한다. 현재 로컬 DB 검증이 모든 환경의 안전성을 대신하지 않는다.
